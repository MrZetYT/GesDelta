### D-002: Документированность

- **Дата:** 06.10.2026
- **Вопрос:** Что изменяет агент? Какие документы?

### D-007: LLM-провайдер

- **Дата:** 08.10.2026
- **Вопрос:** Какие модели и как подключаем?
- **Выбрано:** Единый интерфейс (Microsoft.Extensions.AI). OpenRouter (бесплатные модели) основной, Ollama резервный. Смена модели = правка конфига
- **Почему:** Слабый ноутбук, высокая производительность не нужна; для обзоров по шаблону хватает простых локальных или бесплатных моделей
- **Чем пожертвовали:** Стабильностью: лимиты бесплатных моделей (риск 75% в Vision)
- **Когда пересмотреть:** при частых сбоях или упоре в лимиты

### D-012: Идентичность Material

- **Дата:** 08.10.2026
- **Вопрос:** Как понять, что это та же статья, что и в прошлый раз?
- **Выбрано:** Ключ `(source_id, external_id)`. external_id: guid для RSS, id для arXiv, канонический URL (без utm, фрагмента, хвостового слэша) для остальных
- **Чем пожертвовали:** Если источник сменит URL у страницы без guid, она будет считаться новым Material
- **Когда пересмотреть:** при частых дублях
- Уточнено в D-033 (arXiv)

### D-013: Шум и удаление

- **Дата:** 08.10.2026
- **Выбрано:** Правка без новой информации (опечатка, дата, счётчик) = шум: Snapshot сохраняется, Change не создаётся. Новая информация = значимое изменение. «Удалено» вне MVP: пропавший из выдачи Material не трогаем
- **Почему:** Шум не должен попадать в журнал; RSS показывает только последние N записей, пропажа не значит удаление
- **Когда пересмотреть:** если понадобится отслеживать удаления

- **Почему:** Понятия это то, что извлекается при разборе; в Vision для них нет требований
- **Когда пересмотреть:** если понадобятся связи между понятиями

### D-015: Claim как сущность

- **Дата:** 08.10.2026
- **Вопрос:** Хранить утверждения структурно или только текстом в markdown?
- **Выбрано:** Claim: текст, цитата, ссылка на Snapshot
- **Почему:** Код проверяет, что ссылка есть и цитата найдена в тексте источника; иначе проверка хрупкая. Подтверждения вынесены в отдельную таблицу ClaimEvidence: один Claim, много цитат из разных снимков.
- **Чем пожертвовали:** LLM должна отдавать структурированный JSON; подсчёт «N источников» (группировка одинаковых утверждений) сложнее, чем кажется
- **Когда пересмотреть:** если группировка окажется слишком ненадёжной

### D-024: Планировщик
- **Дата:** 09.10.2026
- **Вопрос:** Своё расписание или Quartz?
- **Выбрано:** В MVP свой цикл (BackgroundService + PeriodicTimer), расписание в БД, всё за интерфейсом `IScheduler`. Quartz.NET на дипломный этап как вторая реализация
- **Почему:** В MVP одна тема и один интервал, задача сводится к проверке «прошёл ли интервал с последнего запуска». Quartz оправдан при нескольких темах и cron-выражениях
- **Чем пожертвовали:** Свой код планировщика (около 30 строк) придётся заменить
- **Когда пересмотреть:** при нескольких темах или cron-расписании

### D-025: Обратная связь между шагами

- **Дата:** 09.10.2026
- **Вопрос:** Нужны ли возвраты между шагами и где именно?
- **Выбрано:** Петля только вокруг Analyzer: Critic (код) проверяет JSON, наличие и подлинность цитат; при отказе Analyzer получает причину и повторяет, максимум 3 попытки. Возврат Parser → Collector как петля графа убран. Повторы внутри Collector только при временных сбоях (сеть, 5xx, 429)
- **Почему:** Parser детерминирован: на тех же данных даст тот же результат, повтор бессмысленен. LLM недетерминирована, повтор с замечанием может дать другой ответ
- **Чем пожертвовали:** Смысловые ошибки («вывод не следует из текста») код не ловит
- **Когда пересмотреть:** На дипломе добавить LLM-критика; раньше, если доля повторов будет высокой

### D-026: Reporter на диплом

- **Дата:** 09.10.2026
- **Выбрано:** В MVP результат запуска = новая версия Description + `summary` в Change. Reporter (полноценный отчёт по Run, сохраняется как Document с `kind = Report`) делаем на дипломном этапе
- **Почему:** Ближе к Суть.md («что было, что нового»), но не нужен для критериев готовности MVP
- **Чем пожертвовали:** В MVP нет связного отчёта «что было / что нового» за период, только журнал по Change

### D-027: Analyzer возвращает правки, а не документ

- **Дата:** 09.10.2026
- **Вопрос:** Analyzer переписывает описание целиком или возвращает правки?
- **Варианты:** A: переписывает весь документ / B: возвращает операции, код собирает версию
- **Выбрано:** B. Операции только `add_section` и `append_to_section`. Один вызов Analyzer на один Change. Версия Description одна на Run: принятые правки копятся в памяти запуска, следующий Change видит описание с уже применёнными правками, файл пишется в конце
- **Почему:** Потеря прежних сведений (риск 70% в Vision) невозможна по построению: старый текст LLM не трогает. Больше работы у кода, меньше у LLM. Правки проверяются по частям. Десять материалов в один промпт не влезут в контекст бесплатной модели
- **Чем пожертвовали:** Связность текста (описание лоскутное), нельзя заменить устаревший факт
- **Когда пересмотреть:** Если бесплатные модели не тянут строгий JSON с операциями, вернуться на A с автосравнением до/после. «Переписать для связности» на диплом вместе с Reporter

### D-028: Незавершённые изменения

- **Дата:** 09.10.2026
- **Вопрос:** Что если запуск упал после сохранения Snapshot, но до Analyzer? (при следующем запуске хэш совпадёт, изменение потеряется)
- **Выбрано:** У `changes` поле `status`: Pending / Done / Failed / Skipped. Snapshot и Change создаются в одной транзакции, Change со статусом Pending. Change становится Done только в финальной транзакции Run вместе с версией описания. Каждый запуск сначала добирает Pending. Failed (3 попытки исчерпаны) автоматически не повторяется. Skipped = материал не относится к теме. Уточнено в D-053 (Skipped также для Change, только подтвердившего существующие Claims).
- **Почему:** Изменение не теряется при сбое, повторный Analyzer стоит токенов, но надёжнее потери данных
- **Чем пожертвовали:** После падения запуска Analyzer вызывается повторно для всего, что не дошло до коммита
- **Когда пересмотреть:** Если повторные вызовы будут упираться в лимиты бесплатных моделей

### D-029: Фиксированный конвейер в MVP, тулы и IRunPipeline как точка перехода

- **Дата:** 10.10.2026
- **Вопрос:** Оркестрация фиксированным сценарием программиста или агент сам планирует шаги? Как закрыть вопрос «в чём автономность»?
- **Варианты:** A: фиксированный конвейер / B: LLM-планировщик сразу
- **Выбрано:** A в MVP. Оркестратор за интерфейсом `IRunPipeline` (`FixedRunPipeline` сейчас, `AgenticRunPipeline` на диплом). Возможности агентов оформлены как stateless-тулы за интерфейсами в Core, чтобы на дипломе отдать их LLM через `AIFunctionFactory`
- **Почему:** Бесплатные модели плохо тянут планирование и строгий JSON (риск 75% в Vision). Запуск без изменений должен стоить 0 токенов (D-009). Автономность MVP: запуск по расписанию, догоняющий запуск, значимость, релевантность и содержание правок, повторы при сбоях
- **Чем пожертвовали:** Порядок шагов зашит, агент не выбирает «что делать дальше». Немного больше интерфейсов
- **Когда пересмотреть:** Дипломный этап, или если модель стабильно тянет вызов функций

### D-030: Структура решения

- **Дата:** 10.10.2026
- **Выбрано:** Проекты Core / Storage / Tools / Agents / Orchestrator / App / Tests. UI знает только фасад `IMonitoringService` из Core. Run state в памяти (`RunContext`), в БД только `runs` и `changes.status`. Агенты ходят в БД напрямую через DbContext (интерфейсы репозиториев не вводим). Change обрабатываются строго по очереди
- **Почему:** Тонкий UI (D-003), меньше кода, возобновление через Pending (D-028). Следующий Change должен видеть описание с правками предыдущего (D-027)
- **Чем пожертвовали:** Тесты агентов с БД идут на Testcontainers (медленнее моков). App ссылается на Orchestrator ради регистрации DI
- **Когда пересмотреть:** Если тесты станут слишком медленными (вводим репозитории) или появится несколько тем (параллельные запуски)

### D-031: Повторы и цепочка моделей

- **Дата:** 10.10.2026
- **Вопрос:** Что делать при лимитах и недоступности LLM, кроме ожидания?
- **Варианты:** A: только повторы и Pending / B: автосвап по цепочке моделей
- **Выбрано:** B. Цепочка из конфига: основная бесплатная OpenRouter → вторая бесплатная → Ollama. Свап по 429, сети, 5xx, таймауту после повторов, держится до конца Run. Отказы Critic не триггерят свап. `FallbackLlmClient : ILlmClient`, пользователь видит уведомление, причина пишется в `runs.stats`. Вся цепочка лежит: Change остаётся Pending, принятое коммитится. Повторы Collector через Microsoft.Extensions.Http.Resilience. `MaxTokensPerRun` в конфиге, по умолчанию выключен
- **Почему:** Лимиты бесплатных моделей главный риск (75%, Vision), D-007 уже делает смену модели конфигом. Агенты про цепочку не знают
- **Чем пожертвовали:** Разные модели дают разное качество JSON. Локальная модель на слабом ноутбуке может не потянуть, и описание может не влезть в её контекст
- **Когда пересмотреть:** Если свапы частые или Ollama стабильно не проходит Critic

### D-032: Расписание, статусы запуска, прерывание

- **Дата:** 10.10.2026
- **Вопрос:** Когда повторять неудачные запуски, как закрывать зависшие, что делать при выходе из приложения?
- **Выбрано:** Цикл раз в минуту. Если последний Run Failed или с `stats.pending > 0`, следующая попытка через `RetryDelay` (1 ч), максимум 3 «нечистых» Run подряд, затем обычный `check_interval` и запись пользователю. Счётчик считается по `runs`. Статусы: NoChanges (очередь пуста), Succeeded (очередь обработана или остановлена по п.3), Failed (БД, все источники при пустой очереди, исключение, таймаут, interrupted). При старте приложения Running → Failed (`interrupted`). «Выход» из трея отменяет запуск без коммита, Change остаются Pending. Ручной запуск при Running отклоняется
- **Почему:** Без RetryDelay после падения или остатка Pending ждали бы весь интервал. Лимит серии защищает от долбёжки мёртвого API. Mutex гарантирует один экземпляр, поэтому закрытие Running безопасно
- **Чем пожертвовали:** При «Выход» накопленные правки запуска теряются, Analyzer вызывается заново (токены). Дополнительная нагрузка на лимиты при повторах
- **Когда пересмотреть:** Если потери при «Выход» окажутся ощутимыми (дождаться конца Change и закоммитить), или при нескольких темах

### D-034: Правила источников

- **Дата:** 10.10.2026
- **Вопрос:** Как задаются источники, что с анонсами RSS, сколько материалов брать, как вести себя вежливо
- **Выбрано:** Типы Rss / Arxiv / Html, тип выбирает пользователь (автоопределения нет). RSS: `fullText = auto` (лента, если длиннее 1500 символов, иначе страница), после первого запуска режим не меняется. Html: одна страница = один Material, обхода нет. - **Чем пожертвовали:** RSS показывает только последние N записей: не вошедшие в потолок новые материалы могут выпасть из ленты раньше, чем мы их соберём. Смена режима `fullText` потребовала бы новых снимков. Без ETag лишние скачивания (нагрузка мизерная)

### D-035: QA: типы, ответы шаблоном, без памяти

### D-040: Подключение к LLM и контракт ILlmClient

### D-044: Логи и трассы LLM

- **Дата:** 10.10.2026
- **Вопрос:** Где хранить логи и как разбирать «агент вернул чушь»?
- **Варианты:** A: логи в БД / B: файлы Serilog + отдельная трасса на каждую LLM-попытку
- **Выбрано:** B. Serilog в файлы, rolling по дням, 30 дней, `%LOCALAPPDATA%/<проект>/logs`. В обычный лог только метаданные. Каждая LLM-попытка отдельным JSON в `logs/llm/{runId}/change-{id}-try-{n}.json` (QA: `logs/llm/qa/{qaId}.json`): промпты, сырой и очищенный ответ, вердикт Critic, модель, `promptVersion`, токены. - **Чем пожертвовали:** Трассы содержат тексты материалов и занимают место (30 дней). Просмотр руками, не из интерфейса. Простой код чистки трасс

### D-052: Вердикт OverBudget и порядок очереди материалов

- **Дата:** 10.10.2026
- **Вопрос:** Что делает Detector с новым Material, когда бюджет `MaxNewMaterialsPerRun` исчерпан? Кто строит порядок «по кругу по источникам»?
- **Варианты:** A: использовать `Skipped` / B: отдельный вердикт `OverBudget` и счётчик
- **Выбрано:** B. Вердикт `OverBudget`, счётчик `stats.overBudget`, в БД ничего не пишется, материал в следующий запуск снова «новый». `Skipped` остаётся только для Change нерелевантных материалов. Очередь (round-robin, свежие вперёд) формирует Оркестратор после Parser, Detector считает бюджет. Заодно: `last_seen_at` обновляется при любом вердикте, кроме `ParseError` и `OverBudget`
- **Почему:** Не смешиваем «отложен из-за потолка» и «нерелевантен». В 06 не было шага бюджета, в 03 не было вердикта. Detector остаётся простым: один материал за раз, без знания об источниках
- **Чем пожертвовали:** Ещё одно значение вердикта и счётчик. Оркестратор получает чуть больше логики
- **Когда пересмотреть:** Если материалы будут теряться из-за выпадения из RSS-ленты (D-034)

### D-053: Change, который только подтверждает существующие Claims

- **Дата:** 11.10.2026
- **Вопрос:** Что делать с Change, где `relevant = true`, есть `confirms`, но нет `operations`? Critic №9 такое пропускает
- **Варианты:** A: Skipped, Evidence пишутся, в журнал не попадает / B: Done с записью «Подтверждено» в журнале
- **Выбрано:** A. Такой Change получает `Skipped` в финальной транзакции вместе с Evidence, `done_at` не заполняется, новая версия описания не создаётся, если других правок нет. `summary` остаётся от Analyzer. Счётчик `stats.confirmOnly`. Финальная транзакция выполняется и тогда, когда есть только Evidence
- **Почему:** B ломает инвариант 01 («правки Done включены в версию описания») и правило «группа журнала = версия» (09), а `sinceLastRun` показывал бы последним «подтверждено», перекрывая реальное обновление. «Подтверждено N источниками» при A работает, схема БД не меняется
- **Чем пожертвовали:** `Skipped` теперь значит «не потребовал правки описания»: нерелевантный и подтверждающий различаются только счётчиками (`skipped` и `confirmOnly`) и логом. Пользователь не видит в журнале, что утверждение получило ещё один источник, это видно только в сносках
- **Когда пересмотреть:** Если пользователю понадобится видеть подтверждения в журнале

### D-055: Закрытие Run входит в финальную транзакцию

- **Дата:** 11.10.2026
- **Вопрос:** Кто и когда ставит `runs.status`, `stats`, `finished_at`, `tokens_used`? Если это отдельная запись после финальной транзакции, а приложение упало между ними, данные закоммичены, а Run остаётся Running и становится `interrupted`
- **Варианты:** A: отдельная запись после коммита / B: обновление `runs` внутри финальной транзакции
- **Выбрано:** B для Run, где есть что коммитить. `NoChanges`, `Failed` и Run без коммита (все Change Failed или нерелевантны) закрываются короткой отдельной записью. Если БД недоступна, Run остаётся Running и закрывается как `interrupted` при старте. Закрывает Run оркестратор, агенты `runs` не трогают
- **Почему:** Коммит данных и закрытие Run атомарны: нет состояния «данные есть, Run висит Running». Расписание (07, раздел 5) считает «нечистые» Run по `runs`, поэтому статус и `stats` должны быть верными
- **Чем пожертвовали:** Финальная транзакция чуть больше. Две ветки закрытия (в транзакции и отдельной записью), обе надо покрыть тестами
- **Когда пересмотреть:** Если закрытие Run станет сложнее (несколько тем, параллельные Run)

### D-056: База для diff это снимок последнего Change, а не последний снимок

- **Дата:** 18.10.2026
- **Вопрос:** После `Noise` снимок сохраняется и становится «прошлым». Две правки по 150 символов дают два `Noise` подряд, суммарная информация никогда не станет Change. Относительно чего считать diff?
- **Варианты:** A: от `new_snapshot_id` самого свежего Change материала / B: от последнего снимка, зафиксировать как ограничение
- **Выбрано:** A. Базовый снимок = `new_snapshot_id` самого свежего Change материала (любой статус). Хэш на `Unchanged` и проверка ошибки разбора по-прежнему против последнего снимка любого вида. `prev_snapshot_id` у `Updated` = база. Индекс `changes(material_id, id DESC)`
- **Почему:** Мониторинг не должен пропускать медленно растущие страницы вроде «What's new». Шумовые снимки продолжают храниться, терять данные не приходится. Правка небольшая
- **Чем пожертвовали:** Абзац, который раньше был шумом, может позже попасть в Change вместе с другими добавками. Diff читает на один снимок больше (базу)
- **Когда пересмотреть:** Если на реальных данных будут повторные ложные срабатывания от накопленного шума

### D-060: Вежливость к хостам: Crawl-delay и чистый URL при докачке

- **Дата:** 06.11.2026
- **Вопрос:** У `habr.com` в `robots.txt` для `User-agent: *` стоит `Crawl-delay: 10`, а в 05 пауза на хост 1 с. Кроме того, запрещены адреса с `utm_` в query, а `<link>` в ленте именно такой (`?utm_campaign=...#habracut`). Как докачивать страницы статей и какую паузу держать?
- **Варианты:** A: пауза 1 с для всех, `Crawl-delay` игнорируем / B: пауза на хост задаётся в конфиге, `IRobotsPolicy` не читает `Crawl-delay` / C: `IRobotsPolicy` сам отдаёт `Crawl-delay`, пауза берётся из него
- **Выбрано:** B. Пауза для отдельных хостов переопределяется в конфиге (`habr.com` = 10 с), для остальных остаётся `HostDelayMs`. Докачка страницы идёт по `guid` или по `link` без query и фрагмента, а не по `link` из ленты как есть
- **Почему:** Правило вежливости из 05 (раздел 8) должно выполняться, а не только быть записанным. B даёт это без усложнения `IRobotsPolicy`: достаточно одного значения в конфиге. Чистый URL нужен, потому что `robots.txt` запрещает `/*?*utm_`, и ссылка из ленты не прошла бы проверку. На 20 записей при паузе 10 с докачка занимает около 200 с, для запуска раз в неделю это нормально
- **Чем пожертвовали:** Значение паузы дублирует `robots.txt` и устареет, если Habr его поменяет. Для нового хоста с `Crawl-delay` придётся вручную добавлять строку в конфиг. Запуск с докачкой стал заметно дольше
- **Когда пересмотреть:** Если источников с `Crawl-delay` станет несколько, перейти на вариант C (`IRobotsPolicy` читает `Crawl-delay` сам). Также если докачка начнёт упираться в таймаут запуска (60 мин, 07)
