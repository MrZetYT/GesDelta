# 09. Формат документов

Отчёта как сущности в MVP нет (D-026). В MVP два выходных документа: Description (файл) и Changelog (представление над БД). Reporter на диплом (раздел 6).

## 1. Description: файл

Файл `.md`, неизменяемая версия: `documents/{topic}/description/v0001.md`, `v0002.md`, ... (04, D-019).

```markdown
# Гибридные интеллектуальные системы

## Нейросимвольный подход

Нейросимвольные системы (neurosymbolic systems) сочетают обучаемые представления и логический вывод. [c:12] Такой подход применяют там, где нужны объяснимые решения. [c:12][c:15]

## Применение в робототехнике

Гибридные системы используют для планирования действий робота. [c:21]
```

> Пример выдуманный, показывает формат.

Правила формата:
- Первая строка `# <тема>`. Её пишет код, не Analyzer.
- Разделы `## Заголовок`. Других уровней заголовков нет.
- `sectionId` = slug заголовка (01). Заголовки уникальны по slug.
- **slug:** нижний регистр, пробелы в `-`, удаляются все символы кроме букв, цифр и `-`, повторные `-` схлопываются, `-` по краям обрезаются. Кириллица без транслитерации. Пустой slug недопустим.
- После каждого факта маркер Claim `[c:42]`, где 42 это `claims.id`. Маркер ставится в конце предложения после точки, через пробел. Несколько подряд: `[c:42][c:43]`. Разбор: регулярное выражение `\[c:(\d+)\]`.
- Метку «N источников / один источник» в файл не пишем: версии неизменяемы, а число источников растёт. UI считает её по БД.
- Файла нет, пока ни один Change не стал Done. UI в этом случае пишет «описание появится после первого запуска».

## 2. Правила для содержимого

| Правило | Значение |
|---|---|
| Длина | `summary` до 400 символов, `content` одной операции до 2000 (конфиг, ниже) |
| Язык | русский: описание, заголовки разделов, показываемые цитаты. Термин по-русски, оригинал в скобках при первом упоминании. Оригинал цитаты хранится в БД |
| Ссылка на источник | у каждого абзаца минимум один маркер. Это проверяет Critic |
| Уверенность | показывает UI по БД: «один источник» / «подтверждено N источниками» (D-005) |

"Description": { "SummaryMaxChars": 400, "ContentMaxChars": 2000 }

## 3. Как код собирает версию

Таблицы БД не пишутся до конца Run. Единственное обращение к БД по ходу: резервирование id Claim из sequence (D-037).

1. Для каждого нового Claim из `claims` ответа резервируется id: `SELECT nextval('claims_id_seq')` (D-037). Получаем соответствие `c1 → 42`.
2. В `content` операций `[[c1]]` заменяются на `[c:42]`.
3. Операции применяются к описанию в памяти: `add_section` добавляет `## заголовок` и текст в конец файла, `append_to_section` добавляет абзац в конец раздела. Существующий текст не меняется.
4. В `RunContext` добавляются: новые Claims (с готовыми id) и их Evidence (`snapshot_id` = `new_snapshot_id` текущего Change, `quote_original`, `quote_ru`). Для `confirms` добавляется только Evidence к существующему Claim, из БД или из этого же Run.
5. `existingClaims` для следующих Change = Claims из БД + Claims из `RunContext`. Так «N источников» работает и внутри одного запуска.
6. Change с `relevant = false`: `Skipped` сразу (07).
7. Change с `relevant = true` без `operations` (только `confirms`): Evidence копятся в `RunContext`, в памяти Change остаётся Pending до финальной транзакции, затем Skipped. `done_at` не заполняется, `stats.confirmOnly++`.

В конце Run, если были правки описания или новые Evidence:
1. Если есть операции: проверка, что каждый маркер `[c:id]` итогового текста указывает на известный Claim.
2. Если есть операции: файл `vNNNN.md` на диск.
3. Одна транзакция: `claims` (с зарезервированными id), `claim_evidence`, `document_versions` (только если были операции), `changes`: `Done` + `summary` + `done_at = now()` для Change с операциями, `Skipped` для Change только с `confirms`, и обновление `runs`: `status = Succeeded`, `stats`, `finished_at`, `tokens_used`.
4. Откат транзакции: `runs` закрывается отдельной короткой записью как `Failed` с `error`, Change остаются Pending (07, раздел 7).

При упавшем Run зарезервированные id остаются неиспользованными. Дыры в нумерации безвредны.

## 4. Журнал изменений (Changelog)

Представление над `changes`, не таблица и не файл (D-016).

- Группируется по `done_at`: все Change одного коммита имеют одно значение, группа = одна версия описания.
- Заголовок группы: «Обновление дд.мм.гггг чч:мм».
- Строка записи: `Новое / Обновлено · summary · заголовок материала, ссылка`.
- Только `Done`. Failed и Pending пользователь видит в «что система делает сейчас».
- Запуск без Change в журнал не попадает (01).
- Новые группы сверху. Подгрузка по группам: `Changelog.GroupsPerPage` = 20 (конфиг), `@before` = `done_at` последней показанной группы. Группа всегда приходит целиком.

## 5. Показ в UI

- `[c:42]` превращается в сноску `[1]`. По клику: заголовок материала, дата (публикации или получения), ссылка, `quote_ru`, пометка «один источник / подтверждено N источниками» (N = число разных Material среди Evidence, считает UI по БД).
- Маркер на несуществующий Claim: показывается `[?]`, в лог `warning`.
- Если открыть `.md` вне приложения, будут сырые `[c:42]`. Экспорт «чистого» md со сносками после MVP.

## 6. Отчёт Reporter (диплом)

В MVP не реализуется (D-026). Задел:

- **Структура:** Что было → Что нового → Что изменилось → Источники.

- **Путь:** `documents/{topic}/reports/{runId}.md`, неизменяемый файл, `documents.kind = Report`.
- **Отчёт «изменений нет»** не создаётся (01, 06).
- **Эталонный отчёт:** пишем вручную на дипломном этапе, по реальным данным первых прогонов. TODO.
