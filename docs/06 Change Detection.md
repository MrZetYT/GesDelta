# 06. Обнаружение изменений

## 1. Определение

Изменение = значимое отличие нового снимка Material от предыдущего (см. 01_DOMAIN, раздел 3).

- Новый Material → `New`, сравнение не нужно (при первом запуске это норма, D-013).
- Существующий Material: добавлена новая информация → `Updated`.
- Остальное (опечатки, даты, счётчики, реклама, переписанные другими словами абзацы, удаления) → шум: Snapshot сохраняется, Change нет.

## 2. Нормализация текста перед сравнением

Нормализуется то, что идёт в `clean_text`. Хэш считается от `clean_text`.

- [ ] RSS / arXiv API: берём поля записи (title, summary/abstract, content), HTML внутри очищаем. Для Rss текст берётся из ленты или со страницы по config.fullText (05). Смена режима даёт новые Snapshot.
- [ ] HTML-страницы: извлекаем только основной контент статьи (SmartReader / AngleSharp), навигация, комментарии, блоки «похожие», реклама не попадают
- [ ] Удаление HTML-разметки
- [ ] Приведение пробелов и переводов строк; регистр для хэша не меняем (разделение абзацев сохраняем: оно нужно для diff)
- [ ] Удаление динамических блоков: даты вида «обновлено …», счётчики просмотров/комментариев
- [ ] TODO: уточнять список по реальным источникам (правила добавляем по мере ложных срабатываний)

Правила нормализации покрыты юнит-тестами (11_QUALITY).

## 3. Уровни проверки

| Уровень | Метод | Что даёт | Стоимость |
|---|---|---|---|
| 1. Точное совпадение | SHA256 от clean_text | изменилось / нет | ноль |
| 2. Размер и характер правки | diff по абзацам (DiffPlex), добавленные абзацы, пороги | шум / значимое | ноль |
| 3. Смысл (вне MVP) | эмбеддинги, косинусное сходство | значимое / нет по смыслу | токены / модель |

Уровень 3 вне MVP, но оформлен интерфейсом `ISignificanceJudge`. Сейчас реализация одна, на правилах уровня 2. Добавление эмбеддингов = вторая реализация (дипломный этап).

### Алгоритм для существующего Material

1. Получили текст, нормализовали → `clean_text`, `content_hash`.
2. Проверка на ошибку разбора (раздел 6). При ошибке выходим, снимок не сохраняем.
3. Хэш совпал с **последним снимком материала (любого вида)** → обновляем `materials.last_seen_at`, дальше ничего (`Unchanged`).
4. Хэш отличается → находим **базовый снимок**: `new_snapshot_id` самого свежего Change этого материала (любой статус: Pending, Done, Failed, Skipped). Diff по абзацам идёт от базового снимка к новому. Шумовые снимки базой не становятся.
5. Считаем чисто добавленные абзацы относительно базы, применяем пороги.
6. В одной транзакции: сохраняем Snapshot и, если значимо, Change (`Updated`, `status = Pending`, `prev_snapshot_id` = базовый снимок). Если шум: только Snapshot. В той же транзакции обновляем `materials.last_seen_at` (при любом вердикте, кроме `ParseError`).

Проверка ошибки разбора (шаг 2, «короче 20%») по-прежнему идёт против последнего снимка любого вида. У каждого Material есть хотя бы один Change (его создаёт вердикт `New`), поэтому база всегда существует.

### Алгоритм для нового Material

1. Получили текст, нормализовали → `clean_text`, `content_hash`.
2. Проверка на ошибку разбора (пустой текст). При ошибке выходим.
3. Бюджет `MaxNewMaterialsPerRun` исчерпан: выходим, Material не создаём, вердикт `OverBudget`, `stats.overBudget++`. В следующий запуск материал снова «новый» (05, раздел 5).
4. В одной транзакции: создаём Material, Snapshot и Change (`New`, `status = Pending`). Сравнение не нужно, Analyzer получает `clean_text` целиком.

## 4. Пороги

Стартовые значения, подбираем на реальных данных. Хранятся в конфиге.

| Параметр | Значение | Обоснование |
|---|---|---|
| Минимальная длина абзаца, чтобы считаться добавленным | 40 символов | Отсекает подписи, одиночные заголовки, обрывки |
| Суммарная длина добавленных абзацев для «значимого» | 200 символов | Примерно 2-3 предложения новой информации |
| Сходство для признания абзаца «правкой» | ≥ 0.8 | Переписанный абзац не считается новой информацией |
| Порог ошибки разбора | новый текст < 20% от предыдущего или пустой | Капча, заглушка, сломанный селектор |

## 5. Кто решает значимость

Код, по правилам раздела 3-4. LLM в решении не участвует. LLM вызывается только Analyzer-ом, когда значимость уже решена. Следствие: запуск без изменений стоит ноль токенов (граница код/LLM, D-009).

Известные ограничения MVP:
- Правка цифры или факта без добавления абзаца (85% → 87%) пройдёт как шум.
- Удаление информации не фиксируется (D-013), но снимок сохранён, доработать можно позже.
- Перефразированный абзац с новым смыслом может быть принят за правку.
- Проверка ошибки разбора (шаг 2, «короче 20%») по-прежнему идёт против последнего снимка любого вида. У каждого Material есть хотя бы один Change (его создаёт вердикт `New`), поэтому база всегда существует.

## 6. Если изменений нет

- Конвейер останавливается без вызова LLM.
- `runs.status = NoChanges`.
- В `runs.stats` пишутся счётчики (полный список в 04, таблица runs).
- В Serilog: «проверено N, изменений нет».
- В журнал для пользователя запись не попадает. На экране статуса можно показывать «последняя проверка: <дата>» (дёшево, берётся из `runs`).

### Ошибка разбора

- Условие: пустой текст или длина < 20% от последнего снимка.
- Снимок не сохраняется, Change не создаётся, источник/материал помечается в `runs.stats.failed` и логе.
- Запуск продолжает работу с остальными материалами и источниками.
